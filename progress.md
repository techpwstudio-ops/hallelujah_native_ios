# G-Hallelujah iOS — Native Rewrite Roadmap

A native SwiftUI rebuild of the existing Flutter app, feature for feature, with a
Liquid Glass interface and a hard focus on scroll/playback smoothness.

**Work through this file top to bottom, one task at a time.** Each task is sized to
be a single session's work. Do not start a task before its milestone's predecessors
are done — the ordering encodes real dependencies (nothing can play audio before the
audio engine exists; CarPlay cannot list playlists before the library does).

## Decisions

Locked in. Revisit only with a reason.

| # | Decision | Rationale |
| --- | --- | --- |
| D1 | SwiftUI + MVVM (`@Observable` view models) | Modern default; least ceremony for a large screen count |
| D2 | Single app target, layered folders (`Core` / `DesignSystem` / `Domain` / `Data` / `Features`) | What every iOS dev recognises; extract to SPM packages later if build times demand it |
| D3 | Minimum iOS **17.0** | `@Observable`, SwiftData, modern `NavigationStack` |
| D4 | Three environments: Development (localhost), Staging (QA), Production | Mirrors `AppConfig` in Flutter, which hardcodes this behind `isDebug = true` |
| D5 | Dark-first theme, gold accent `#FFC857` | Matches `lib/theme/colors.dart`; the Flutter app is dark-only |
| D6 | Config flows xcconfig → Info.plist → `AppConfiguration` | No host, key, or flag literal anywhere in Swift |
| D7 | Swift 6 language mode, strict concurrency `complete` | New codebase — cheaper now than retrofitted |
| D8 | `project.yml` (XcodeGen) is the source of truth for `GHallelujah.xcodeproj`; `project.pbxproj` is a generated artifact | Hand-editing a synchronized-groups pbxproj is error-prone; XcodeGen 2.45+ supports Xcode 16 synced folders. Add targets/schemes/configs in `project.yml`, then run `xcodegen generate`. `xcodegen` is installed at `~/.local/bin/xcodegen` (on `PATH`) — installed from the GitHub release zip, not Homebrew, since Homebrew on this machine refuses all installs over an unrelated tap-trust issue (untrusted `mongodb/brew`, `dart-lang/dart`, `shivammathur/php` taps) |
| D9 | The DI composition root is named `AppComposition`, not `AppEnvironment` | T02 already used `AppEnvironment` for the deployment-environment enum (development/staging/production) before T03's roadmap text ("registration in `AppEnvironment`") was implemented — kept the enum name since it's referenced everywhere, named the composition root something else instead |
| D10 | Splash screen (T15) and every auth screen (T21–T24) must match the Flutter app's UI exactly — no layout/visual changes. Under-the-hood improvements (performance, accessibility, code quality) are fine as long as nothing visible changes | User directive, 2026-09-16. When picking up those tasks: read the actual Dart widget tree (`lib/views/splash/**`, `lib/views/auth/**` or equivalent) for exact spacing/copy/assets, not just the general Liquid Glass design system rules — those tasks are the one place pixel parity beats the new design system |
| D12 | **Exact parity with the Flutter app, everywhere** — same flow, same layout, same look (spacing, colours, type sizes/weights, copy, assets). Supersedes D10's "splash + auth only" limit and D11's system-font choice. Liquid Glass is used only where the Flutter app itself renders glass (iOS 26 mini player, glass bottom nav — see `docs/glassy_bottom_nav_bar.md`) and as the OS-native rendering of those same surfaces, never as a redesign | User directive, 2026-10-14: "only migrate from Flutter, everything migrated, exactly same flow and look". ## Non-negotiables

Applied to **every** task. A task is not done if it violates one of these.

**Nothing hardcoded**
- Hosts, ports, keys, feature flags → `Config/*.xcconfig` → `Info.plist` → `AppConfiguration`.
- Colours, spacing, radii, typography, durations → design tokens. No `Color(hex:)`, no `.padding(16)`.
- User-facing text → String Catalog (`Localizable.xcstrings`). No string literals in views.
- API paths → `Endpoint` values in `Data/Endpoints`, never inline in a repository.

**Glass UI**
- Every raised surface (nav bar, tab bar, sheets, mini player, cards, overlays) goes through
  the `GlassSurface` primitive from the design system. No ad-hoc `.ultraThinMaterial`.
- On iOS 26+ it uses native Liquid Glass (`.glassEffect`, `GlassEffectContainer`);
  below that it falls back to the material + stroke + highlight recipe. One primitive,
  two implementations, decided in one place. **See Open question Q1.**

**Smoothness** — this is a music app; jank is a bug
- 120 fps target on ProMotion. Budget: 8 ms/frame.
- Lists are lazy, rows have stable identity, artwork is downsampled to its display size
  and prefetched ahead of scroll.
- Nothing blocking on the main actor: decoding, disk I/O, image work all off-main.
- No blur over scrolling content without a `GlassEffectContainer` / rasterised layer.
- Every list-bearing task is profiled in Instruments (Animation Hitches) before it is ticked.

**Definition of done** (per task)
- Builds clean for Debug + Release, zero new warnings.
- Unit tests for domain/data logic; SwiftUI previews for every new view, light and dark.
- No `TODO` left without a task number next to it.
- Checkbox ticked, Status log updated.

Answer before the task that depends on it.

- **Q1 (blocks T11) — Liquid Glass vs iOS 17 floor. ADOPTED 2026-09-16:** went with
  recommendation (a) — kept the 17.0 floor, `GlassSurface` (T11) hides both
  implementations behind one call site. Validated against the Flutter app itself while

  else. This isn't just the safer option for a 17.0 floor, it's what the reference app
  ships today.
- **Q2 (blocks T07) — Local store. ADOPTED 2026-09-16:** went with the
  recommendation — GRDB (added as an SPM package in `project.yml`, no tables
  yet — `DatabaseMigrator.empty`, each feature task adds its own migration as
  it defines a table). Downloads still get plain files (T46), not GRDB.
- **Q3 (blocks T61) — Razorpay on iOS.** Confirm which purchases legitimately go through
  Razorpay vs StoreKit, since App Review requires StoreKit for digital content.
- **Q4 (blocks T76) — Migration. ANSWERED 2026-09-16:** existing Flutter users must
  keep their session on upgrade — no forced re-login. This is really a T06 (Session,
  tokens, auth interceptor) constraint, not just a T76 one. **Deferred 2026-09-16 by
  user direction**: T06 shipped the native session/token store fresh (starts empty),
  without the Flutter migration. Still needed before release: `KeychainTokenStore`
  (`App/Core/Security/`) has a doc comment marking exactly where this plugs in.
